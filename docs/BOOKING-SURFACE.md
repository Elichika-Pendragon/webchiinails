# Booking form: direction and scope

Mode: Operate. Extend the existing Chii white/blush/rose visual system and its rounded controls. The owner specifies five editable fields plus calculated DP and a constant URL; this is a direct form extension, not a redesign.

Use one readable form with three semantic groups: customer details, amounts agreed during consultation, and a two-hour WIB appointment. On desktop, put a compact explanation alongside the form. On mobile, keep labels and inputs in one column; show amount pairs only where both remain comfortable. **Book** stays disabled until all five editable fields pass shared validation; the deposit remains read-only. Inline errors appear after a field is left. A successful action prepares the summary/fallback WhatsApp anchor and immediately opens WhatsApp, without another mandatory review step. The customer still presses **Kirim** in WhatsApp. The prepared summary and editing option remain available when returning to the page.

The route checks `GET /api/booking/status` once on entry, with an explicit retry after a failure. An explicit `{ enabled: false }` retains the clearly labelled WhatsApp-only preview, without server submission, approval links or Calendar claims. Unknown status, a timeout, or malformed JSON blocks Book and preserves the form; a failing online request never silently downgrades to the preview. The online path posts canonical name, WhatsApp digits, agreed price as a digit string, date, time and an in-memory idempotency key to `/api/booking/requests`. Only a validated pending response with a same-origin `/book/approve?r=<43-character token>` link may be included in the prepared WhatsApp message. No client-generated or simulated approval link is used.

The random idempotency key is reused for retries of the same canonical five fields and replaced when those values change. It exists only in page memory; neither customer details nor keys are stored in local/session storage. A busy lock prevents duplicate submissions, fetches abort after 12 seconds or departure, and an inactive page cannot redirect after a late response. Date/time options still describe operating hours, not occupied/free slots. The API validates again; actual payment and quote checks remain with Chii, and Calendar confirmation follows an authenticated owner acceptance.

DP is automatically 10% of the agreed total, read-only, rounded up to whole rupiah and recalculated by shared validation. The selected payment wording is transfer or QRIS with Chii's manual payment check through WhatsApp. No payment API or gateway is activated. No receiving details are known, so the summary asks Chii to confirm payment instructions in the existing conversation. Use Last book 14:00 Monday–Friday and 10:00 on weekends; studio closing remains 17:00/12:00.

The amount label is **DP 10%**. Date selection is an inline Indonesian month calendar with six fixed Monday-first rows, constrained month buttons and keyboard navigation. Keep date selection explicit, use the shared WIB bounds, retain the native date field until enhancement succeeds, and update the same time selector. Disabled days indicate the date range only, never actual occupied slots. Preserve the selected date across review/edit and focus the calendar from date-error links. At 320px, dense day targets may be approximately 42px wide with 44px height; they must remain inside the viewport without horizontal scrolling.

Keep existing logo, typography, header height and theme. Reuse the static header/footer; no React hydration, extra font, external embed, polling or new image is needed. Status and request calls are same-origin and no-store, with no-referrer on the page and fetches. Include native labels, 44px or larger controls, visible keyboard focus, associated field errors, an error summary, reduced-motion support and a no-JavaScript explanation.

The form lives at /book, outside existing navigation and sitemap with noindex; Jessica shares this constant URL after consultation. Do not add Book/Booking to the header, menu or public booking sections. The owner approval interface is documented in [APPROVAL-SURFACE.md](APPROVAL-SURFACE.md). Its availability is controlled by backend configuration; implementing the interface does not establish that owner login, request storage or Calendar writes are activated. Working defaults of 30-minute start spacing and 90-day horizon are provisional technical choices, not owner-approved availability policies.

Rendered browser and deployed API checks are recorded by the release owner separately.
