# Booking form: direction and scope

Mode: Operate. Extend the existing Chii white/blush/rose visual system and its rounded controls. Keep the original five required booking values plus defaulted native payment, design-type and duration choices; derive the read-only upfront amount. The URL stays constant; this is a direct form extension, not a redesign.

Use one readable form with three semantic groups: customer details, amounts agreed during consultation, and a consulted-duration WIB appointment. On desktop, put a compact explanation alongside the form. On mobile, keep labels and inputs in one column; show amount pairs only where comfortable. **Book** stays disabled until all original values and payment/design/duration choices validate and an online slot is confirmed available. The amount is read-only. The original values, payment/design/duration selections and private proof upload are required; no freeform design/service description or manual payment-amount input is added. Inline errors appear after a field is left. Success prepares the summary/fallback WhatsApp anchor and opens WhatsApp without another mandatory review step; the customer still presses **Kirim** there. The summary and editing option remain available on return.

The route checks `GET /api/booking/status` once on entry, with an explicit retry after a failure. An explicit `{ enabled: false }` retains the clearly labelled WhatsApp-only preview, without server submission, approval links or Calendar claims. Unknown status, a timeout, or malformed JSON blocks Book and preserves the form; a failing online request never silently downgrades to the preview. The online path posts canonical name, WhatsApp digits, agreed price, date/time, paymentMode, designType, durationMinutes as a digit string and an in-memory idempotency key to `/api/booking/requests`. Only a validated pending response with a same-origin `/book/approve?r=<43-character token>` link may be included in the prepared WhatsApp message. No client-generated or simulated approval link is used.

The random idempotency key is reused for retries of the same canonical booking values, payment mode/policy, design and duration, and replaced when that immutable payload changes. Changing mode must not reuse an older amount/link. Keys exist only in page memory; no local/session storage is used. A busy lock prevents duplicate submissions, receipt-upload POST aborts after 30 seconds, status/availability/owner reads after 12 seconds, and all abort on departure. Inactive pages cannot redirect after a late response. Online POST /api/booking/availability with JSON {date,designType,durationMinutes:string} returns only date/design/duration/timeZone plus slots of time and available boolean. Date/design/duration changes recheck occupancy; loading/error states block Book. Google busy and D1 accepted/approving/reconcile claims block overlap, while pending requests do not hold. A native time select remains fallback until the 46px slot grid renders; busy/elapsed candidates disable, selected is rose. Explicit disabled mode is clearly labelled hours-only preview. The API validates again; actual payment/quote checks remain with Chii, and Calendar confirmation follows authenticated owner acceptance.

Latest policy: `paymentMode=deposit` calculates `min(total, max(20000, ceil(total / 10)))`; `full` calculates the total. Totals at/below Rp20.000 normalize to full payment. `deposit` remains the API field for the actual selected upfront amount; remaining balance is total minus that amount. New requests use `paymentPolicy=min20k-v2`; old records use mode `legacy`/policy `legacy-10pct-v1` and retain their stored 10% amount. Invalid public modes, including `legacy`, are rejected; an omitted old-client mode defaults to deposit. Transfer/QRIS payment is still checked manually by Chii; selecting full payment does not prove it has been paid. Regular Last book stays 14:00 weekdays/10:00 weekends, closing 17:00/12:00. Full art caps at 12:00 and must fit before closing: weekend 3h latest 09:00, 4h 08:00, 5h unavailable.

Preserve date/mode/design/duration on edit and recheck affected slots. Disabled days show only date bounds, never occupied slots. At 320px, dense day targets may be about 42px wide with 44px height; no horizontal overflow is allowed.

Keep existing logo, typography, header height and theme. Reuse the static header/footer; no React hydration, extra font, external embed, polling or new image is needed. Status and request calls are same-origin and no-store, with no-referrer on the page and fetches. Only authenticated owner review may fetch the image, after an explicit **Lihat bukti** action; summaries expose at most `hasPaymentProof`, never an image/public URL. Pre-receipt legacy requests have no uploaded proof. A screenshot is customer-supplied evidence for Chii to check, not automatic payment verification. No R2, billing or automatic WhatsApp attachment is introduced. Receipt migration 0004 is applied as two successful CREATEs without rewriting old rows; combined feature verification/publication and cleanup deployment remain pending.

To close an entire day, Chii uses an ordinary all-day **Busy** event in the existing Nail Art Calendar. Removing it reopens the day subject to other busy events/claims.
