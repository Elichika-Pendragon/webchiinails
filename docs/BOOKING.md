### Atomic holds and cross-service races

Reservation cannot use a JavaScript read-then-write or a unique start timestamp alone: 09.00–11.00 and 10.00–12.00 overlap despite different starts. This implementation claims `durationMinutes / 30` consecutive 30-minute cells, from two cells for 60 minutes to ten for 300 minutes, with a unique slot-start constraint. Legacy two-hour requests retain four cells. A D1 batch atomically changes the pending request to `approving` with an operation/lease and inserts every required interval claim; a constraint failure rolls back that batch. Bound statements and operation checks protect the subsequent state changes. No outbox operation or scheduled retry worker is used. [D1 batch semantics](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).

## Durable states, retries and expiry

These are the implemented D1 request states. The enabled service now persists pending requests; only explicitly disabled WhatsApp-preview mode avoids persistence. A saved request or WhatsApp handoff must not be labelled paid or accepted merely because the customer clicked Book.

| State | Meaning |
| --- | --- |
| `pending` | Stored immutable request with canonical DP and an expiring lookup reference; no Calendar event or guaranteed reservation. Opening the link cannot approve it. |
| `approving` | An explicit owner acceptance holds all selected-duration interval cells under a fenced operation/lease while checking availability before a write. No event success is implied. |

| `accepted` | The matching private Calendar event has been acknowledged or recovered, and its ID plus the deciding owner's identity are stored. Payment verification is the owner's manual attestation. |
| `cancelled` | The owner explicitly cancelled a pending request; this action does not delete an accepted Calendar event. |
| `expired` | The unapproved request reached its expiry/start boundary and cannot be accepted. Expiry is not deletion or a refund. |
